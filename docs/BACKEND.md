# Backend — техническое устройство

NestJS 11 + Prisma + PostgreSQL, REST + WebSocket. Что за продукт —
`OVERVIEW.md`, стек — `Tech-spec.md`.

В разделах помечено, что **есть** в коде и что **план** (этап N). Когда план
становится кодом — пометка снимается в том же коммите.

### Слои внутри модуля

- **Контроллер** — маршрут, guard, роль, DTO, Swagger. Без `prisma.*` и
  бизнес-правил.
- **Сервис** — правила и транзакции. Единственное место, где модуль ходит в
  Prisma.
- **Mapper** — строка БД → DTO ответа. Ответ никогда не содержит
  `passwordHash` и внутренних полей.
- **Gateway** (orders) — только рассылка событий и подписка; изменение
  статуса идёт через сервис.

## 2. Авторизация и роли

- Глобальные guards (есть, `APP_GUARD` в `app.module.ts`): `JwtAuthGuard` →
  `RolesGuard`. Порядок важен: сначала кто, потом можно ли.
- `@Public()` — без входа; `@Roles('manager', 'admin')` — список ролей;
  без декоратора — любой вошедший. Без входа — `401 «Нужно войти»`, без
  роли — `403 «Недостаточно прав»`.
- JWT: payload `{ sub: userId }`, срок — `JWT_TTL_SECONDS`. **Роль в токене не
  хранится**: `JwtStrategy` на каждый запрос берёт пользователя из БД, поэтому
  смена роли и отключение (`isActive = false`) действуют сразу.
- Cookie `access_token`: `httpOnly`, `sameSite: 'lax'`, `secure` в проде,
  `domain` — `COOKIE_DOMAIN`. Токен в теле ответа не отдаётся. Выход —
  `clearCookie` с теми же опциями.
- Вход: одно сообщение «Неверная почта или пароль» и для чужой почты, и для
  неверного пароля, и для отключённого — не выдаём, кто зарегистрирован. Для
  несуществующей почты argon2 всё равно считается на подставном хеше
  (`verifyPasswordOrDummy`), чтобы время ответа не выдавало почту.
- Новый пароль (регистрация, сотрудник) — декоратор `@NewPassword()` из
  `common/password-policy.ts`: 8–128 символов, хотя бы одна буква и одна
  цифра. Форма регистрации на фронте проверяет то же — менять вместе. Вход
  сложность не проверяет: старые пароли продолжают работать.
- Хеш — argon2id с параметрами библиотеки по умолчанию (64 МиБ, 3 прохода,
  4 потока) — выше минимума OWASP.
- Регистрация — только клиенты (`role` в теле отклоняется ValidationPipe);
  сотрудников создаёт админ. Почта хранится в нижнем регистре, пробелы по
  краям обрезает `@Trim()`.
- Лимит: `ThrottlerGuard` на входе и регистрации, 10 запросов в минуту с IP,
  дальше — `429` с русским `message` и `Retry-After` (секунды). IP за прокси берётся из `X-Forwarded-For` только на
  `TRUST_PROXY` прокси вглубь (`main.ts`); при 0 все клиенты за прокси
  делят один счётчик.
- Заголовки безопасности — `helmet()` в `configureApp` (CSP по умолчанию
  подходит Swagger UI).
- **Первый админ** — при старте API из `ADMIN_EMAIL` и `ADMIN_PASSWORD`
  (`users/admin-bootstrap.service.ts`, `OnApplicationBootstrap`). Без ручек,
  секретных путей и скриптов:
  - пользователя нет — создаётся админ; есть админ — не трогается (пароль,
    сменённый позже, не затирается);
  - есть, но **не админ** — молча не повышается, в логе предупреждение:
    иначе заранее зарегистрированный на сайте клиент получил бы админку со
    своим паролем;
  - `ADMIN_RESET_PASSWORD=true` — роль «админ», аккаунт включён, пароль из
    env (чужой перестаёт работать); после входа флаг убрать;
  - переменные проверяет `config/env.ts`: только вместе, пароль от 12
    символов и не равен почте, сброс — только с ними; иначе API не стартует.
    В логи и ошибки не попадают ни почта, ни пароль;
  - два экземпляра стартуют одновременно — второй ловит `P2002` и считает
    админа существующим.
  Уже выданные сессии сброс не обрывает (JWT без версии): при компрометации
  сменить и `JWT_SECRET`.
- `GET /auth/me` — текущий пользователь; им пользуется фронт для redirect.

### Сотрудники (есть)

- Только админ (`@Roles('admin')` на `UsersController`). Создаёт сотрудника с
  временным паролем (роль — бариста, менеджер или админ; клиента так не
  создать — `400`), меняет роль, отключает и включает (`isActive`).
- **Себя изменить нельзя** (`409`): ни роль, ни отключение. Так в системе
  всегда остаётся хотя бы один действующий админ — правит только админ.
- Клиента через `PATCH /users/staff/:id` не изменить — `404`.
- Новая роль и отключение действуют сразу, без перевыпуска токена: роль
  берётся из БД на каждый запрос (§2).
- Смены пароля и «забыл пароль» пока нет.

### Популярные позиции (есть)

- `GET /menu/popular` — открытая витрина для главной: позиции по числу строк
  заказов с ними (`orderItems`, отменённые тоже считаются — это интерес
  гостей), при равенстве и пока заказов нет — по порядку меню.
- Архив и стоп-лист не отдаются: на витрине — только то, что можно заказать.
- `limit` — 1–12, по умолчанию 4; иначе `400`.

### Метки позиций (есть)

- В ответе меню у каждой позиции — `badges`, готовый список по порядку
  важности: `popular`, `new`, затем ручные `seasonal`, `signature`, `decaf`.
  Правила — чистые функции в `menu/menu-badges.ts`.
- `popular` — режим `popularOverride`: `null` (авто) — топ-5 позиций по
  сумме порций (`quantity`) за последние 30 дней без отменённых заказов, не
  меньше 3 порций; `true` — всегда; `false` — никогда. В панели позиция
  отдаёт ещё `autoPopular` — что дал бы режим «авто».
- Витрина `/menu/popular` считает по заказам за всё время, но учитывает
  решение менеджера: `true` — первыми, `false` — не показываются.
- `new` — пока `newUntil` в будущем. Новая позиция получает срок +14 дней,
  если менеджер не передал `newUntil`; `null` — снять метку.
- Ручные метки — `manualBadges` в `POST/PATCH /menu/items`, enum `MenuBadge`.
  В панели (`/menu/manage`) позиция отдаёт и `manualBadges`, и `newUntil`.

### Добавки (есть)

- `ModifierGroup` — группа («Молоко»): `kind` — `single` (один вариант),
  `multiple` (несколько, до `maxSelect`) или `quantity` (количеством, всего до
  `maxSelect`); `required` — без выбора товар не добавить. `ModifierOption` —
  вариант: надбавка `priceDelta` (целые тенге, 0 — бесплатно), `isDefault`,
  стоп-лист, подпись `note` («+150 мл»).
- Группа заводится один раз и подключается к товарам
  (`MenuItemModifierGroup`, порядок — у товара): `PUT /menu/items/:id/modifier-groups`.
- Правила выбора и цена — чистые функции `menu/modifier-selection.ts`, одни для
  заказа и для `defaultPrice` в меню (цена с вариантами по умолчанию; `null` —
  по умолчанию не собрать, гость выбирает в шторке).
- Варианты правятся по одному (`POST …/options`, `PATCH/DELETE
  /menu/modifier-options/:id`): их id не меняются, корзины гостей остаются
  верными. Настройки, при которых товар не собрать (два варианта по умолчанию в
  «один»), — `400`.
- Размер — обычная группа `single` с надбавкой: отдельных товаров на размеры нет.

### Фото позиций (есть)

- Строки — `MenuItemPhoto` (key, width, height, hasAlpha, sortOrder), файлы — в
  хранилище: `<key>-320.webp`, `-800`, `-1600`, где key = `menu/<itemId>/<uuid>`.
  Первое фото по `sortOrder` — обложка. Не больше 6 у позиции.
- Загрузка (`menu-photo-processing.ts`): тип — по содержимому (JPEG, PNG,
  WebP, AVIF; HEIC — нет), до 10 МБ, от 200 px по меньшей стороне; поворот по
  EXIF, метаданные (GPS) не сохраняются; прозрачный фон определяется сам.
- Сначала проверяются все файлы, потом грузятся: один плохой файл — `400`, и
  ничего не загружено. Сбой записи в БД — загруженные файлы удаляются.
- Удаление фото, позиции или уход позиции в архив удаляет и файлы (ошибка
  удаления файла — только предупреждение в логе).
- Ошибки multer («File too large») переводятся на русский —
  `photo-upload-error.filter.ts`.
- Хранилище не задано (`S3_*` пусто) — меню работает, загрузка отвечает `503`.
  Вне прода API при старте создаёт бакет с открытым чтением.
- В ответе меню у позиции `photos` (размеры и адреса трёх файлов) и `slug` —
  для ссылки на товар; slug — транслит названия, при переименовании не меняется.

### Управление меню (есть)

- `@Roles('manager', 'admin')` на всём `MenuAdminController`.
- Новая позиция и категория — в конец (`sortOrder` = последний + 1).
- `PATCH` позиции меняет только переданные поля; пустая строка в
  `description` / `portion` — очистить (`@TrimToNull()`).
- Категорию с позициями удалить нельзя — `409`; пустую — `204`.
- Slug категории — транслит названия (`slug.ts`), дубль получает `-2`, `-3`;
  при переименовании slug не меняется, чтобы не ломать ссылки `#якорь`.
- Порядок категорий — `PUT /menu/categories/order` с id **всех** категорий,
  одной транзакцией; неполный список — `400`.
- Удаление позиции сейчас окончательное. С заказами (этап 5) позиция,
  попавшая в заказ, должна скрываться, а не удаляться — `onDelete: Restrict`
  на `OrderItem` это обеспечит.

## 3. API и ошибки

- Префикс `/api` и Swagger (есть): UI — `/api/docs`, JSON — `/api/docs-json`.
  Тот же документ без запуска сервера — `pnpm openapi:export`.
- Ответ — DTO ответа без обёртки; список без пагинации — массив
  (`GET /menu` → `MenuCategoryDto[]`).
- Пути — существительные во множественном числе, `kebab-case`; поля JSON —
  `camelCase` (как в Prisma и TS).
- Списки с пагинацией — `{ items, total, page, pageSize }`.
- Ошибки — исключения Nest (`NotFoundException`, `ForbiddenException`,
  `ConflictException`) с русским `message`; HTTP-статус несёт смысл, тело 200
  с ошибкой не отдаётся.
- Позиция в стоп-листе при заказе — `409 Conflict` с понятным сообщением.
- Ломающее изменение DTO — в описании PR, чтобы фронт перегенерировал типы.

## 4. БД и Prisma

- Модели (есть): `MenuCategory` (slug, name, sortOrder), `MenuItem`
  (name, description, portion, price, imageUrl, inStopList, badges, newUntil,
  popularOverride, sortOrder).
  Наружу `inStopList` уходит как `isAvailable` — видна, но не заказать.
- Модели (есть): `User` (email, passwordHash, role, name, isActive),
  `Order` (userId, status, total, comment, pickupAt) и `OrderItem`
  (menuItemId, name и price — копия на момент заказа, quantity).
- `MenuItem.isArchived`: позиция, которая есть в заказах, при удалении
  уходит в архив (скрыта из меню и панели, заказать нельзя), а не удаляется —
  `OrderItem.menuItem` с `onDelete: Restrict`. Категорию, где остались только
  архивные позиции, удалить нельзя (`409`), но она пустая и на сайте не видна.
- Таблицы и колонки — `snake_case` через `@@map`/`@map`, поля в коде — `camelCase`.
- Цена в `OrderItem` копируется при создании: правка меню не меняет старые
  заказы.
- Деньги — `Int` в целых тенге, не `Float`.
- Создание заказа с позициями — одна `$transaction`.
- Переход статуса — проверка допустимого перехода в сервисе
  (`new → accepted → preparing → ready → completed`, `cancelled` — из `new`
  и `accepted`).

### Заказы (есть)

- Оформляет только клиент. В запросе — `menuItemId`, `quantity` и выбранные
  добавки (`modifiers: [{ optionId, quantity? }]`); **цен в запросе нет**
  (лишние поля — `400`). Позиции, добавки и цену за штуку проверяет и считает
  `MenuService.resolveOrderLines` (модуль заказов в таблицы меню не ходит).
- Одна позиция может прийти несколькими строками — с разными добавками; до 20
  штук в строке и до 30 строк.
- `expectedTotal` — сумма, которую видел гость; не совпала с расчётом — `409`
  «Цены в меню изменились…»: корзина обновляется, молча другую сумму не берём.
- Позиция или вариант добавки в стоп-листе, исчезнувшая добавка — `409`;
  неверный выбор (обязательная группа, лимиты) — `400` с названием группы.
- В строке заказа `price` — за штуку вместе с добавками; добавки копируются в
  `OrderItemModifier` (группа, вариант, надбавка, количество, был ли по
  умолчанию): правка или удаление добавки в меню старые заказы не меняет.
- `pickupAt` — от «сейчас» (5 минут на часы клиента) до суток вперёд; не
  передан — «как можно скорее».
- Переходы — `orders/order-status.ts`: `new → accepted → preparing → ready →
  completed`, `cancelled` — из `new` и `accepted`. Недопустимый — `409` с
  названиями статусов.
- Смена статуса — `updateMany` с условием на прежний статус: два бариста
  одновременно не переведут заказ дважды (второй получит `409`).
- Очередь — активные заказы (`new`…`ready`), старые сверху, с именем клиента.

## 5. WebSocket (есть)

- `OrdersGateway` (socket.io), namespace `/orders`. CORS и cookie —
  `SocketIoAdapter` в `main.ts` (тот же `FRONTEND_URL`, `credentials`).
- Вход проверяет middleware namespace (`afterInit` → `server.use`), до
  подключения: токен из `handshake.auth.token` (сайт на другом домене:
  берёт его через `GET /auth/socket-token`, JWT на 60 с с `purpose: 'socket'`,
  для REST не годится) или cookie `access_token` из заголовка
  (`readAccessToken`, тот же домен) → `AuthService.userFromToken` (подпись, срок,
  активный пользователь). Нет — `connect_error` с `unauthorized`, события
  `connect` клиент не получает и повторяет попытку сам (фронт — с растущей
  паузой). Комнаты: `user:<id>` всем,
  `staff` — бариста, менеджеру, админу.
- События, **после** записи в БД:
  - `order.created` → `staff`, `StaffOrderDto`;
  - `order.updated` → `staff` — `StaffOrderDto`, `user:<владелец>` —
    `OrderDto` (без имени клиента).
- Один процесс API; несколько инстансов потребуют Redis-адаптер socket.io.

## 6. Окружение

Переменные проверяются zod-схемой `src/config/env.ts` при старте: неполный
env роняет приложение сразу с перечнем ошибок. Читать — через
`ConfigService<Env, true>` с `{ infer: true }`, не через `process.env`.
Новая переменная — в схему и в `.env.example` в том же PR.

| Переменная | Для чего | Есть |
| --- | --- | --- |
| `NODE_ENV` | `development` / `test` / `production` | ✔ |
| `PORT` | порт API, по умолчанию 4000 | ✔ |
| `DATABASE_URL` | строка подключения PostgreSQL | ✔ |
| `FRONTEND_URL` | разрешённый origin для CORS, по умолчанию `http://localhost:3000` | ✔ |
| `JWT_SECRET` | подпись JWT, минимум 32 символа | ✔ |
| `JWT_TTL_SECONDS` | срок токена и cookie, по умолчанию 604800 (7 дней) | ✔ |
| `COOKIE_DOMAIN` | домен cookie в проде (`.cofelier.kz`); пусто — текущий хост | ✔ |
| `TRUST_PROXY` | сколько прокси перед API доверять в `X-Forwarded-For` (IP для лимита входа), по умолчанию 0 | ✔ |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | первый админ при старте API (только вместе, пароль от 12 символов) | ✔ |
| `ADMIN_RESET_PASSWORD` | `true` — разово сбросить роль, доступ и пароль этого аккаунта | ✔ |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_PUBLIC_URL` | хранилище фото меню; все вместе или ни одной (без них загрузка фото — `503`) | ✔ |
| `S3_REGION` | регион S3: `us-east-1` локально (RustFS), `auto` на R2; по умолчанию `auto` | ✔ |
| `E2E_DATABASE_URL` | только для `pnpm test:e2e`: своя база с именем на `_test` (приложение не читает) | ✔ |

## Правила

**Процесс**

- Код — источник истины; док правится в том же коммите, что и поведение.
- Объём задачи не расширять молча; неоднозначность — спросить.
- Удаление и исправление — разные коммиты.

**Код**

- Файл больше 300–400 строк — делить. Сервис не знает про `Request`/`Response`.
- Полные имена; DTO — `CreateMenuItemDto`, `MenuItemResponseDto`.
- Комментарий — одно предложение про «почему».
- `console.*` в `src` нельзя — `Logger` из `@nestjs/common` с контекстом.
- Форматирование — `.prettierrc` (одинарные кавычки, trailing comma).

**Безопасность**

- Не логировать пароли, токены, cookie, тела запросов авторизации.
- Сырой SQL — только параметризованный.
- Rate limit на `/auth/login` и `/auth/register` (`@nestjs/throttler`), IP — с учётом `TRUST_PROXY`.

**Язык.** Комментарии, доки и `message` ошибок — русский; идентификаторы,
коммиты, ветки — английский.
